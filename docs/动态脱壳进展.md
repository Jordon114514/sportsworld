# 动态脱壳（运行时 Dump）进展

时间：2026-11-07
设备：OnePlus PJZ110 / Android 17（root / KernelSU）
目标：绕过易盾的方法抽取保护，从内存拿到完整业务字节码

---

## 一、为什么需要动态 dump

静态分析发现：**145 个业务 Activity 中 141 个无法反编译**。

根因不是 jadx 的 bug，而是 DEX 里**方法体被抽走了**：

| 类 | 方法总数 | 有 code_item | 无 code_item |
|---|---|---|---|
| `RunPlanActivity` | 70 | 33 | **37（53%）** |
| `AiCameraActivity` | 12 | 6 | **6（50%）** |
| `BaseActivity` | 86 | 84 | 2（2%） |

那 33 个有 code_item 的偏移 `0x59fec8~0x5a035c` 全部合法落在 data 区内，说明剩下的 37 个方法**在 DEX 里根本没有代码数据**。

易盾在运行时把抽走的字节码回填到内存，所以理论上：**dump 运行中进程的内存，就能拿到完整代码**。

---

## 二、已完成的探测

### 2.1 定位含 DEX 的内存区域

用 `grep` 在设备端逐区域扫描 DEX 魔数（`dex\n035`）：

```bash
# 对每个可读区域执行
dd if=/proc/$PID/mem bs=4096 skip=$((0xADDR/4096)) count=$N | grep -abo 'dex.035'
```

**第一轮**（只扫 `dalvik-DEX data` 区域，13 个）：仅 1 处命中，但 PID 变化后失效。

**第二轮**（扫全部可读区域，941 个）：

```
HIT 189 0x7ae6200000 18874368 [anon:libc_malloc]
HIT 205 0x7aed574000 507904  .../base.apk
HIT 208 0x7af17ae000 71639040 .../oat/arm64/base.vdex
HIT 209 0x7af5c00000 4194304 [anon:libc_malloc]
```

### 2.2 分析已 dump 的区域

#### `base.vdex`（71.6 MB，已 dump）

VDEX 027 格式，头部解析：

```
magic: vdex027
number_of_dex_files: 4
dex[0] offset=0x40        size=71634936
dex[1] offset=0x4451038   size=715
dex[2] offset=0x4451304   size=260
```

提取 dex[0]：**68.32 MB，但只有 30 个类**——这是易盾壳自身的类（`com.netease.NetSecKit.*`），**不含业务代码**。

dex[1]/dex[2] 尺寸太小（715 / 260 字节），不是有效 DEX。

#### `libc_malloc` 18 MB 区域（已 dump）

偏移 `0xc00000` 处发现 DEX：

```
file_size = 2,298,884 (2.19 MB)
classes   = 2,186
```

但解析后发现 **`com/zjwh` 类为 0**——是某个 SDK 的 DEX，不是业务代码。

该区域另有 `RunPlanActivity` 字符串（`0x8eaa49`），但格式是**点号分隔**（`com.zjwh...RunPlanActivity`），属 ART 的**类名缓存**，不是 DEX 字符串常量。

## 三、全量扫描结果

### 3.1 方法

dump 全部 **762 个可读区域**（共 1.65 GB）到 `/data/local/tmp/full/`，然后用 `od` 十六进制搜索定位 DEX 魔数：

```bash
# grep 对二进制不可靠（'.' 被当正则通配），改用 od
od -An -tx1 -v "$f" | tr -d ' \n' | grep -o '6465780a3033' | wc -l
```

> 踩坑：`grep -c 'dex.035'` 对含 `\n` 的二进制会漏匹配（`.` 匹配不到换行），必须用十六进制搜索。

### 3.2 结果

```
HIT r0005.bin dexmagic=29 size=4325376
HIT r0095.bin dexmagic=1  size=2818048
```

**只有 2 个区域含 DEX 魔数**，其中 `r0005.bin`（4.3 MB）含 **29 处**。

> 注：`r0005` 对应的实际地址为 `0xaa420000` 附近（`dalvik-cache` 相关区域），而非业务 DEX 所在。

### 3.3 当前状态

设备在准备拉取 `r0005.bin` 时断开连接，分析中断。

**下一步**：重连后拉取并解析 `r0005.bin` 的 29 个 DEX 片段。

## 四、当前判断

### 4.1 业务 DEX 可能已不在常规内存区

多次扫描的结果指向一个结论：**App 启动完成后，业务 DEX 的明文副本可能不在可读匿名内存中**。

可能的原因：

| 假设 | 依据 |
|---|---|
| ART 已把 DEX 转成 oat/art 结构 | `dalvik-DEX data` 区域无魔数，说明已编译为机器码 |
| 壳解密后立即释放 | 业务代码以 oat 形式存在于 `base.oat`，DEX 原文不再保留 |
| 方法体在 native 层动态生成 | 易盾的"方法抽取"可能用 JIT 方式回填，不生成完整 DEX |

如果是第二种，**dump DEX 这条路走不通**，需要改为：
- dump `base.oat`（ART 编译后的机器码）
- 或用 Frida hook `dexFileOpen` 等 ART 内部函数，在加载瞬间截获

### 4.2 vdex 的发现值得注意

`base.vdex` 里 dex[0] 是 68 MB 的壳 DEX（30 个类），与我们静态分析得到的 `classes.dex`（71.6 MB）大小一致。

**但静态那份的字符串表 1061 条、类 30 个**——两者吻合，说明 **vdex 里存的就是原始壳 DEX 的完整副本**，只是业务载荷部分依然是加密的。
