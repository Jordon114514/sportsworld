## 一、Java 层 — 覆盖情况（~93%）

### 已处理

8 个 DEX 全部重建成功并 jadx 反编译：

| 项 | 数值 |

| 语法干净 | 28,362（76.2%） |
| 业务包 `com/zjwh` | 2,803（91.8% 干净） |

### 缺口

| 问题 | 数量 | 性质 |
|---|---|---|
| 含未反编译方法体 | **8,671 文件** | jadx 放弃反编译特定方法 |
| 花括号不平衡 | 222 | 输出被截断 |
| 非法 `.N.` 引用 | 84 | Kotlin 内联 lambda 伪语法 |
| `enum X extends Y` | 88（业务包 0） | Java 禁止枚举继承枚举 |
| **`defpackage` 无法归包** | **4,897 文件** | jadx 无法确定包名，落到默认包 |

**重点**：`defpackage` 那 4,897 个文件是最大缺口。这些是混淆后的匿名类/lambda，jadx 解析不了包名。它们大多属于广告 SDK（`com.byazt.*`、`com.tianmu.*`）和混淆工具类。

### 可补救手段

- 用 **androguard 直接读字节码**（我在 `PointCheckStrategy` 和上传主流程 `emit` 上用过这招，成功绕过 jadx 的注解解析错误）
- 用 **baksmali** 出 smali 再看
- 这 4,897 个类里业务代码占比极低

4. **`libsqlcipher.so`（3.46 MB）** — 解 `sport.db` 需要它的密钥派生方式
