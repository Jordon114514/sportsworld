## 三、业务 DEX 的最终去向（已实锤）

### 3.1 内存扫描结果：0 个业务 DEX

在游客模式下做了三轮不同程度的扫描：

| 扫描方式 | 结果 |
|---|---|
| `Process.enumerateRanges('r--')` 全量扫 dex 魔数 | 命中若干，全部 `file_size=0` 误报 |
| 扫 `Lcom/zjwh/...` DEX 描述符 | **0** |
| 扫 `com.zjwh...` ART 类名缓存 | **0** |
| 扫所有 `(deleted)` 映射 | 0 个业务 dex |

### 3.2 找到了易盾的运行时临时文件（但不是 DEX）

`/proc/self/maps` 中的关键行：

```
4000231c0000-4000231c6000 r--p 00000000 /data/data/com.zjwh.../files/3efbdb8b238fc49bc60df0a3b40999c4.t (deleted)
4000231c9000-4000231ca000 r--p 00005000 /data/data/com.zjwh.../files/3efbdb8b238fc49bc60df0a3b40999c4.t (deleted)
4000231cd000-4000231ce000 rw-p 00005000 /data/data/com.zjwh.../files/3efbdb8b238fc49bc60df0a3b40999c4.t (deleted)
```

**这是易盾运行时释放并从磁盘删除的临时文件**（`.t` 后缀，生命周期极短）。

dump 出来的三个段：

| 段 | 大小 | 类型 |
|---|---|---|
| seg0 | 24,576 B | **ELF**（`7f454c46`，aarch64 动态库） |
| seg1 | 4,096 B | ARM64 指令序列 |
| seg2 | 4,096 B | 同 seg1 |

**结论**：`.t` 是易盾自己的 native 解密器（ELF），不是业务 DEX。它被加载后立即从文件系统删除，属于典型的"文件不落地"保护。

### 3.3 业务数据确实在 base.vdex，且是明文

之前已分析清楚（见 `MuMu脱壳实验报告.md`）：

```
base.vdex  68.22 MB
├── 0x40 ~ 0x1030c    壳 DEX（30 类，头部完全自洽、无改写）
└── 0x1030c ~ 末尾    隐藏区 68.16 MB
    ├── 熵 5.0 左右（明文，非加密）
    ├── 9145 个 Lcom/zjwh/... 类描述符
    ├── 连续合法 string_data 链（最长 3000 条）
    └── code_item 字节码结构
```

**没有嵌套的 `dex\n03x` 头**（全文件仅 0 偏移有一个）。

## 四、结论汇总

### 4.1 已经排除的路径

| 路径 | 结论 |
|---|---|
| 真机（Android 17）frida 注入 | frida 与环境不兼容，非 App 问题 |
| MuMu frida 注入 | ✅ 可用，但 App 检测 `/proc/self/maps` 会自杀 |
| spawn 模式抓解密瞬间 | 抓到的是壳 DEX，业务 DEX 那一瞬没出现 |
| 内存全量 dump | 业务 DEX 不在内存 |
| Android 15 系统 dex 映射区扫描 | 0 个业务 dex |
| 易盾 `.t` 临时文件 | 是 ELF 解密器，不是 DEX |

### 4.2 最终确认的技术事实

1. **MuMu 上 frida 完全可用**（能注入 `system_server`、`logd`、`netd`）
2. **App 有 `/proc/self/maps` 检测**，读取后自杀；绕过一处后仍会死（说明有多处）
3. **游客模式不触发反调试**，可以安全 attach
4. **ART native hook（FindClass/RegisterDexFile）不触发**，必须用 Java 层 hook
5. **业务 DEX 从不在进程内存中以完整 DEX 形式存在**
6. **业务代码以 code_item 形式散落在 base.vdex 隐藏区**，DEX 头与 id 表被剥除
7. **可以正常加载所有业务类**（`Java.use` 成功），说明 ART 有办法把散落的 code_item 组装起来执行

### 4.3 第 7 点是最关键的突破口

既然 `RunPlanActivity`、`HomeActivity` 这些类**能被成功加载并执行**，说明 ART 内部一定有某种机制把 code_item 与 class_data 关联起来。

**这意味着**：数据一定在内存里，只是不在我们扫描的那些区域，或者以 ART 内部结构（`ArtMethod`、`DexCache`）形式存在，而不是原始 DEX 字节。

## 五、下一步建议

### 方案 A：hook ArtMethod 的入口（最有希望）

不在 DEX 层面找，而是在 **ArtMethod 结构**层面找：

1. 用 `Java.use('com.zjwh...RunPlanActivity')` 拿到 Class
2. 通过 JNI 拿到 `jmethodID`，转成 `ArtMethod*`（ART 内部指针）
3. 读 `ArtMethod` 的 `ptr_sized_fields_.data_` / `entry_point_from_quick_compiled_code_`
4. 如果是解释执行，`data_` 指向 `DexCache` + `dex_method_index`

这样能拿到真实的方法体定位信息，绕开"找完整 DEX"的思路。

### 方案 B：hook 解释器的 DexCache（次优）

ART 解释执行时，`DexCache` 里有 `resolved_methods_` 和 `dex_file_` 指针。hook `art::interpreter::Execute` 或 `art::interpreter::EnterInterpreterFromEntryPoint`，从参数里拿 `ShadowFrame`，再拿 `DexFile`。

### 方案 C：JIT 层抓取（如果 App 用 JIT）

MuMu 上发现 `memfd:jit-cache` 和 `memfd:jit-zygote-cache` 两个 32MB 映射，说明 ART 开启了 JIT。hook `art::jit::Jit::CompileMethod` 可以拿到正在编译的方法及其字节码。

### 方案 D：放弃还原 DEX，改为直接调用

既然类都能加载，可以直接在 frida 里：

```javascript
Java.perform(function(){
  var C = Java.use('com.zjwh...RunPlanActivity');
  // 枚举方法、读字段、调静态方法
  C.class.getDeclaredMethods().forEach(function(m){
    console.log(m.getName(), m.getParameterTypes().length);
  });
});
```

这在很多场景下比拿到 DEX 更有用（比如分析反作弊逻辑、还原协议参数）。
