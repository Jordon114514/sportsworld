defpackage/aa      -> com/huawei/hms/hwid/aa

只有 **854 个无法还原**（DEX 里也存在重名，无法唯一匹配）。

## 三、重打包路径的实际评估

### 3.1 理论路径

```
1. 修复 4,043 个 defpackage 文件 → 移回正确的包目录
2. 补回 1,058 个真缺失的业务类（从 DEX 用 androguard 生成 Java 壳）
3. 引入 android.jar（API 33）
4. 引入 Kotlin stdlib + 5,641 个第三方依赖
5. 修复 7,847 个含未反编译方法的文件（这些必须手写或从 smali 补）
6. 用 aapt2 从 APK 提取 res/ + resources.arsc
7. javac 全量编译 → d8 转 dex
8. 替换 APK 里的 classes.dex → zipalign → apksigner 重签
9. 处理签名校验（易盾有，重签必失败）
```

### 3.2 三个硬性阻断

**① 7,847 个文件不可编译**
这些文件的某些方法 jadx 完全放弃（输出 `throw new UnsupportedOperationException("Method not decompiled")`）。要补只能：
- 手写实现（需要理解原逻辑）
- 从 smali 逐条翻译（工作量巨大）
- **留空（运行时必崩）**

**② 混淆不可逆**
全部类名/方法名是 `OooO00o`、`o00000` 这种无意义标识符。即使编译通过，人工维护成本极高。而且：
- Kotlin 的 `@DebugMetadata` 只保留了部分变量名
- 内联函数展开后无法还原
- 协程状态机被压成 `label`/`switch`

**③ 签名校验必然失败**
易盾 `libnesec.so` 会校验 APK 签名。重打包后签名改变 → 壳拒绝加载 → App 无法启动。要绕过需要 patch `libnesec.so`，而它的代码是加密的（`.gnu.fragment` 熵 7.156）。

### 3.3 可行的替代路径

如果目标是"得到一个能跑的 APK"，**正确做法不是重编译源码，而是直接改原 APK**：

```
1. 用 androguard/baksmali 直接修改目标类的方法体（smali 层）
2. 重新打包 + 重签
3. 处理签名校验（hook 或 patch native）
```

这条路径完全绕过了"源码编译"这个瓶颈，工作量小一到两个数量级。

## 五、总结

### 编译价值：**中等偏低**

**能编译的部分**：
- 8,686 个纯 JDK 文件（23.3%）→ 实测 165 个 .class 成功产出
- 423 个完整自包含包
- 这部分可以编译、可以跑单元测试

**不能编译的部分**：
- 7,847 个文件有不可恢复的方法体（21.1%）
- 12,608 个类缺失（18.7%），其中 1,058 个是核心业务类
- 资源层 `res/` 完全缺失
- 签名校验不可绕过

### 一句话

**源码的价值在于"读"和"分析"，不在于"编译"。** 想要可运行的东西，走 smali 层直接改原 APK；想要理解逻辑，现在拿到的源码已经够用。

把 37,224 个文件修到能编译，投入产出比极差——需要补 1 万多个类、7 千多个方法、4 千个资源，而且最终还会因为签名校验跑不起来。
