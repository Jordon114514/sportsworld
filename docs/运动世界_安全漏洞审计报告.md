## 二、严重漏洞详解

### V1 / V2：全局 TLS 校验被完全关闭

**证据**

`httpmanager/net/OooOOO0.java` —— 空实现的 TrustManager：

```java
public final class OooOOO0 implements X509TrustManager {
    public void checkClientTrusted(X509Certificate[] arr, String str) { }   // 空
    public void checkServerTrusted(X509Certificate[] arr, String str) { }   // 空
    public X509Certificate[] getAcceptedIssuers() { return new X509Certificate[0]; }
}
```

`httpmanager/net/OooOOO.java` —— 无条件返回 true 的主机名校验：

```java
public final class OooOOO implements HostnameVerifier {
    public boolean verify(String str, SSLSession session) { return true; }
}
```

`httpmanager/net/OooO00o.java:56-65` —— 两处同时装配到生产 OkHttpClient：

```java
public final OkHttpClient OooO0Oo() {
    OkHttpClient.Builder builder = new OkHttpClient.Builder();
    ...
    builder.sslSocketFactory(OooO0OO(), new OooOOO0());     // 空 TrustManager
    return OooO00o(builder.hostnameVerifier(new OooOOO()))  // true
            .addInterceptor(new OooO()).build();
}
```

`httpmanager/net/OooO00o.java:38-54` 中 `OooO0OO()` 用 `SSLContext.init(null, new OooOOO0[]{new OooOOO0()}, ...)` 生成 socket factory。

**影响面**：`net/OooO0o.java:9` 继承该基类，这是 App 主 API 客户端：

```java
public final class OooO0o extends com.zjwh.android_wh_physicalfitness.httpmanager.net.OooO00o {
```

即**全部业务接口**（登录、跑步记录上传、支付下单、社区）都运行在"任何证书都接受"的信道上。

**危害**

- 任意同一 WiFi 下的攻击者可用自签证书完成完整中间人，读取/篡改全部明文业务数据（Body 虽经 AES 加密，但密钥同在第 V3 条已泄露）。
- 因为 hostnameVerifier 恒为 true，攻击者甚至不需要证书域名匹配。
- 结合 V5 的明文 HTTP 域名，攻击面进一步扩大。

**修复**

```java
// 删除 OooOOO0 / OooOOO 两个类，改用默认校验
OkHttpClient.Builder builder = new OkHttpClient.Builder();
// 如需固定证书，用 CertificatePinner
builder.certificatePinner(new CertificatePinner.Builder()
    .add("run.gxapp.iydsj.com", "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
    .build());
```

`network_security_config` 中移除 `<certificates src="user"/>`（当前 `res/8GD.xml` 对 `i.snssdk.com`、`mi.gdt.qq.com` 等广告域显式信任用户 CA）。

### V3：跑步成绩签名密钥硬编码，可离线伪造

**签名算法**（`utils/o00O00.java`）：

```java
public static String OooO0o0(Map map, String str) {   // 被 signRunRecord 调用
    return OooO0O0(OooOO0(map), str);                  // key 按字典序排序拼接 k=v&k=v
}
public static String OooO0o(String str, String str2) {
    return OooO0OO(str + str2);                        // MD5(拼接串 + 密钥)
}
```

密钥来源：

```java
// o00O00.java:23
return OooO0o0(map, SportJniUtils.getSecretKey(5));    // 索引 5 的密钥
```

**密钥已从原生库定位**（`libswsport.so`，arm64，637,568 字节；`.data` 段 vaddr `0xab000`）：

同一函数中各 `case` 分支直接把静态指针交给 `FUN_0014b634`（C++ string 拷贝构造）返回，**密钥没有任何运行时派生**，就摆在 `.data` 段里：

| index | .data 地址 | 实测内容 |
|---|---|---|
| 0 | `0xab030` | 单字节 XOR 0x80 后可打印 |
| 1 | `0xab060` | 二进制，无单字节 XOR 可还原 |
| 2 | `0xab070` | 二进制，无单字节 XOR 可还原 |
| 3 | `0xab010` | 明文 ASCII |
| 4 | `0xab090` | 明文 ASCII，约 192 字节 |
| 5 | `0xab180` | **成绩签名密钥，二进制（非单字节异或）** |
| 6 | `0xab1b0` | 二进制 |

> 说明：索引 5 的密钥块 `d2 13 14 18 1d d0 ...` 经实测**不是单字节异或混淆**（256 种单字节 XOR 均无法得到可打印 ASCII），因此不能靠简单爆破还原。但这不构成实质防护——密钥既在内存中以明文形态存在，直接 hook `getSecretKey` 或 `signRunRecord` 读取返回值即可，成本远低于逆向还原。复现脚本见 `tools/audit/40_keys.py`。

**危害**

攻击者可以直接在 PC 上复现 `signRunRecord`（或运行时 hook 拿到密钥），对任意伪造的 `UploadFormatEntity` 签名并通过服务端验签——若服务端未对时间/距离/步频做独立交叉校验，本地签名等于没有防护。这是"代跑/刷里程"黑产的技术前提。

**注意**：密钥混淆只能提高逆向成本，无法改变"密钥在客户端即可被获取"这一事实。真正的修复点在服务端。

**修复**

- 签名密钥不得下发给客户端。改为服务端下发的短时效挑战值（nonce）+ 服务端密钥的 HMAC。
- 服务端必须独立校验：轨迹点时间连续性、速度分布合理性、步频与位移一致性、GPS 精度分布、设备传感器可信度。
- 参考同 App 已有的 `SportJniUtils.isValidPoint`（GPS 定位质量门限校验）思路，把校验搬到服务端。

## 三、高危漏洞详解

### V4：上传验签可被中间人剥离，导致成绩静默降级

`mvi/run/mode/UploadRecordPImpl$upload$1.java:111-124`：

```java
if (str != null) {
    if (o00Ooo.OooO0O0(str, "验证签名失败")) {          // 服务端返回"验证签名失败"
        String sign = HttpUtil.signRunRecord2(entity, ...); // 客户端重新签名
        UploadRecordPImpl.access$uploadSing(impl, sign, uuid); // 再次提交
    }
}
```

**危害**：服务端通过错误字符串驱动客户端重签。中间人可先剥离 `signature` 字段使服务端返回"验证签名失败"，客户端随即用本地密钥重签并重传——攻击者无需知道密钥即可让任意 payload 通过验签。

**修复**：服务端验签失败必须直接拒绝并告警，不应设计"客户端重签"流程；签名必须覆盖不可重放字段（时间戳 + nonce）。

### V5：明文 HTTP 与全局明文流量

```java
// utils/Utils.java:266-277
public static String OooO0Oo(String str) {
    return o00O00.OooO0o(("https://run.gxapp.iydsj.com" + str)
            .replace("https://", "http"),           // 强制降级为明文 HTTP
            SportJniUtils.getSecretKey(5));
}
```

且 `AndroidManifest.xml:166` 中 `android:usesCleartextTraffic="true"` 全局放开明文流量。

**危害**：签名计算基于降级后的 HTTP URL，攻击者可在明文信道直接篡改 URL 与响应；同时对 `datapoint.gxapp.iydsj.com` 等埋点域可任意投毒。

**修复**：移除 `.replace("https://", "http")`；`usesCleartextTraffic` 设为 `false`，仅对确需的广告域在 `network_security_config` 中放行。

## 四、中危漏洞详解

### V6：WebView 的 URL 分发逻辑

`mvi/WebViewActivity$OooO0O0.java:164-187`：

```java
public boolean shouldOverrideUrlLoading(WebView view, String url) {
    Boolean allow = (Boolean) o0000O.OooO0O0("sp_allow_secret", Boolean.FALSE);
    if (!allow) {
        // 任意 URL 直接交给系统 Intent
        startActivity(new Intent(ACTION_VIEW, Uri.parse(url)));
        return true;
    }
    if (url.startsWith("zjwhjs://")) return true;
    if (url.startsWith("http")) return super.shouldOverrideUrlLoading(view, url);
    othe.OooO0O0.OooOOo0((Activity) context, url);   // 再走一次外部 App 分发
    return true;
}
```

问题点：

1. 只判断 `startsWith("http")`，`http` 前缀还包括 `httpfoo://` 等畸形 scheme；
2. `sp_allow_secret` 是普通 SharedPreferences 布尔值（`utils/o0000O`），**未做任何完整性校验**——App 可被降级为"任意页面可跳任意 App"；
3. `othe/OooO0O0.java:298` 对 `weixin://wap/pay?`、`alipays://` 等支付 scheme 不做来源域名校验，任何 H5 页面都能拉起支付流程，存在钓鱼支付界面风险。

**修复**：WebView 内跳转必须校验 host 白名单；支付类 scheme 必须校验调用方为自家域名；`sp_allow_secret` 若为安全开关，应放入不可篡改存储（Keystore 加密或签名校验）。

### V7：`zjwh://` DeepLink 无鉴权

`AndroidManifest.xml:173-178` 将 `SplashActivity` 注册为 `zjwh` scheme 的 BROWSABLE 入口，`othe/OooO0O0.java:286-296` 直接分发到内部路由：

```java
if (str.startsWith("zjwh://")) {
    return !OooO(activity, str.substring(7), OooOO0o(uri));  // 参数原样透传
}
```

已确认路由清单（`intel/all_strings.txt`）：

```
zjwh://articleDetail?id=
zjwh://studentInfo?id=
zjwh://topicDetail?id=
zjwh://hotDynamic
zjwh://musicAlbumDetail
```

`zjwh://studentInfo?id=` 可被任意网页/短信/二维码拉起并直接进入指定学生信息页。虽然数据接口仍需登录态，但存在越权查看（IDOR）风险与钓鱼跳转风险。

**修复**：DeepLink 入口必须校验调用来源，敏感路由（如 `studentInfo`）要求二次确认或禁止外部拉起。

### V8：调试入口残留且导出

`AndroidManifest.xml:167`：

```xml
<activity android:name="com.zjwh.android_wh_physicalfitness.hybrid.demo.HybridMultiContainerDemoActivity"
          android:exported="true" android:screenOrientation="1"/>
```

`_rev/src/sources/defpackage/HybridMultiContainerDemoActivity.java` 确认该类存在于正式包（JADX 反编译失败但类元数据可读），配套布局 `activity_hybrid_multi_container_demo`（TabLayout + ViewPager 的多容器调试面板）。

同时 `mvi/setting/SettingActivity` 保留了"信用跑验证调试面板"（`llCreditVerifyDebug`、`btnDebugCreditAbandon`、`btnDebugCreditPopupFirst/Last`、`btnDebugCreditWaiting`），可绕过信用分弹窗流程直接触发放弃/弹窗状态机。

**修复**：删除全部 `*.demo.*` 包与调试面板，或在 `build.gradle` 中用 `releaseImplementation` 剔除并在 CI 中做导出组件基线比对。

### V9：AES 使用不当

`utils/OooO00o.java:13,24-37`：

```java
public String f25516OooO00o = "smkldospdosldaaa";    // 16 字节硬编码密钥
Cipher cipher = Cipher.getInstance("AES");           // 实际为 AES/ECB/PKCS5Padding
cipher.init(2, new SecretKeySpec(f25516OooO00o.getBytes(), "AES"));
```

问题：ECB 模式（相同明文块产生相同密文）、固定密钥硬编码、无完整性保护（可被块重排攻击）。

`utils/rundata/OooO00o.java:73-90` 的 Keystore 封装存在另一处问题：`setUserAuthenticationRequired(false)` + `setRandomizedEncryptionRequired(false)`，且 IV 直接取密文前 16 字节，未与 Keystore 绑定用户认证。

**修复**：改用 `AES/GCM/NoPadding`，密钥由 Android Keystore 生成且不导出，IV 随机并由 Keystore 管理（`setRandomizedEncryptionRequired(true)`）。

### V10：证书固定逻辑形同虚设

`utils/HttpUtil.java:87-107`：

```java
Certificate cert = CertificateFactory.getInstance("X.509")
        .generateCertificate(context.getAssets().open("leichi.crt"));
...
trustManagerFactory.init(keyStore);
```

问题：

1. `assets/leichi.crt` **在 APK 中不存在**（已核验 assets 目录，仅有 `.cert.pem` / `.bks`）。`getSSLContext` 必然抛 `IOException` 返回 null，`send()` 直接 `return false`——即该固定逻辑对应的请求路径事实上从未生效，说明这是一处死代码或遗留缺陷。
2. 即使文件存在，该逻辑用单张自签证书作为唯一信任锚，属于自签名而非真实 CA 固定，无法防御持有该证书私钥的攻击者。
3. `HttpUtil.setAuthorization`（`:119-130`）构造 `Basic base64(username + ":" + psw)`，把**账号明文密码**放进每个请求头。该方法当前未被业务代码调用（已全量检索确认），但属于高危死代码，一旦启用即造成凭据长期泄露。

**修复**：删除 `HttpUtil` 中的 trust-all 与 Basic 认证遗留代码；固定证书改用 `CertificatePinner` 的 SPKI 哈希。

### V11：Cookie 允许第三方

`utils/Utils.java:1331-1357` 的全局 WebView 初始化：

```java
settings.setJavaScriptEnabled(true);
settings.setAllowFileAccess(true);
settings.setMixedContentMode(0);                       // MIXED_CONTENT_ALWAYS_ALLOW
CookieManager.getInstance().setAcceptThirdPartyCookies(webView, true);
```

`setMixedContentMode(0)` 允许 HTTPS 页面加载 HTTP 资源，配合 V1 的 TLS 失守可被注入；第三方 Cookie 允许则扩大了跨站追踪面。

**修复**：`setMixedContentMode(MIXED_CONTENT_NEVER_ALLOW)`；第三方 Cookie 置 false。

### V12：无障碍自动授权 SDK

`com.acse.ottn.service.ShopHelperService`（`AndroidManifest.xml:337`）声明 `BIND_ACCESSIBILITY_SERVICE` 且 `exported="true"`；`res/lNO.xml` 配置的能力组合为：

```
accessibilityEventTypes="0xFFFFFFFF"   全事件
accessibilityFeedbackType="0xFFFFFFFF"
canRetrieveWindowContent="true"        读窗口内容
canPerformGestures="true"              模拟手势
canTakeScreenshot="true"               截屏
isAccessibilityTool="true"             声明为无障碍工具
```

远超"记录运动轨迹"所需，实质是自动点击系统权限弹窗的一键授权实现。同包内还有 9 个 `exported="true"` 的服务与 4 个透明 Activity。

**修复**：评估合规风险；`isAccessibilityTool` 与实际用途不符，应用商店与监管审核存在下架/处罚风险。非必要应整体移除该 SDK。
